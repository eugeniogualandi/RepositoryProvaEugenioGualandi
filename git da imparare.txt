Primi comandi

git --version    serve a vedere la versione di git

git config     serve per impostare configurazioni git

git config --global user.mail "[tua email]"  imposta la tua E_mail a livello globale
	--list  invece da una lista di tutti i parametri come sono configurati
	--global user.name "[tuo nome]" imposta il tuo nome

git help    serve a vedere la lista dei comandi git


Ci sono due modi per avviare un git

o lo cloni o lo inizializzi.

git init     lo inizializzi. crei un nuovo repository.

la scritta master comparirà una volta inizializzato.


03-11-2026

in pratica con

git clone [indirizzo url del repository] [nome cartella dove vogliamo settare working directory]    si va a clonare un repository da un altra fonte.

in una working directory i file possono essere tracciati o non tracciati. una volta tracciato un file, git inizia a fare il versioning.

git add [nome file]   ci permette di iniziare a tracciare un file.

in pratica se cambi un file che hai appena aggiunto, sdoppi il file: c'è il file che verrà aggiunto alla prossima istantanea e il file che non verrà modificato nella prossima istantanea.

dopo aver aggiunto le modifiche con git add, tutto torna a essere pronto per essere fotografato.

con git commit ti apre l'editor di testo preferito per inserire un commento al commit: inserisci il commento e esci salvando.

git log     per vedere il commit andato a buon fine
git log --stat per vedere altre informazioni.
git log --oneline serve per vedere i commit uno per uno per riga.

si consiglia all'inizio di un lavoro, soprattutto se versionato, di aggiungere la licenza; per progetti gratuiti, la licenza mit.

per fare un commit senza aprire l'edito di testo usare
git commit -m

con
git commit --amend puoi sovrascrivere il commit precedente.
questo comando può essere usato anche per cambiare il commento del commti precedente.

git restore serve per scartare le modifiche nella working directory. con l'opzione --staged serve per mettere il file da staged a traked.

git diff serve per vedere tutte le differenze tra l'ultimo commit e i file attuali.



Repository remoti

il comando sarebbe
git remote

però prima bisogna impostarlo: andiamo a prendere il link dalla repository remota.

quindi

git remote add [alias] [link della repository] per settare il link pc-repository
poi
git remote -v    per vedere il link

per allineare il repository remoto con quello locare bisogna usare il push:
git push [nome alias repository remoto][nome ramo bersaglio]

mi sono accorto che ho fatto un push di un amend, che non si potrebbe fare: quindi ho usato la funzione
-f

adesso provo a allineare il repository remoto con quello locale, facendo un commit da remoto.
ricordati di dare la descrizione del commit.

per fare il pull sembra che prima bisogna fare il git fetch --all. in realta con
git pull [nome alias repository remoto][nome ramo target locale] esegue anche il fetch.
il fetch serve per dare un occhiata a quello che succede senza unire il remoto con il locale: si vede con git log --oneline --all

per rinominare un alias locale possiamo usare
-git remote rename [alias vecchio][nuovo nome alias remoto]

per rimuovere un repository remoto invece

-git remote -rm [nome alias repository remoto da eliminare]

ricorda che prima di fare un push o un pull è meglio fare un commit, se no devi forzare il push. in realtà facendo un pull stai facendo una sorta di commit e allineamento dei file attuali con quelli da remoto. comunque prima di effetturare un pull è meglio fare il commit per non avere nulla di traked o in staged non commited.

si fa tutta una serie di azioni che chiedono di risolvere i conflitti: nei file vengono scritti i conflitti. comunque la situazione rimane nel limbo finche non risolvi i conflitti individuati tramite git diff e fatto un git commit. adesso mi manca solo da rimuovere l'etichetta del ramo con git branc -d [nome etichetta da eliminare]

oggi reinizio con la condivisione file fra più utenti. per prima cosa creo un branch nuovo, ci metto un file condiviso, lo pusho in rete e lo vado a riprendere da un'altra cartella locale simulando che sia un'altra persona.

in pratica, quando vai in un nuovo ambiente locale, con il git clone ti mette crea il ramo principale e ti posiziona li. il ramo principale è quello con scritto head nel repository remoto. nel nostro caso, dopo aver settato un untente locale, abbiamo creato e sincronizzato un branch locale con quello remoto di equale nome. poi abbiamo pushato verso internet e infine abbiamo fatto un fetch per aggiornare l'altro locale. ricordati di guardare dove sta la head locale prima di fare modifiche e ricorda di fare il pull. adesso faccio un commit e un merge e un push per allineare tutto(locale1 e internet); ricordati di spostarti nel ramo master prima di fare il merge.
per eliminare i branch che non servono più:

git branch --delete [nome ramo da eliminare locale]
git push [alias repository remoto] --delete [nome ramo remoto da cancellare]

andiamo a riforndare un ramo con il rebase.

creiamo un nuovo ramo:
git ceckout -b [nome ramo] (git branch + cechout grazie a -b)

da quello che ho capito il rebase è un aggiornamento dal ramo master sul ramo secondario. quindi una volta fatto il rebase si può fare un bel fast foward senza conflitti.
il comando, partendo dal ramo secondario che vuoi aggiornare con il master, è
git rebase [nome del ramo principale sul quale aggiornarsi]    in pratica traduco rebase con cambio padre/base.

non fare mai il rebase di qualcosa che hai pushato. in pratica non cambiare l'ash di della storia che sta sotto l'head del ramo remoto. anche amend cambia l'hash.

10-11-2026

oggi imparero lo stash.

git stash push (o senza push)  mette in salvataggio la working directory senza commit.

git stash list serve per vedere i salvataggi

git stashd rop [nome stash] per eliminare uno stash

git stash clear per eliminare gli stash

git stash [nome stash] per riprendere lo stash (senza nome riprende l'ultimo stash)

comunque in pratica lo stash è un branch non commitato del quale fai merging senza commit.


Passiamo a fare i Tag
i tag sono degli alias degli ash.
per codice, il commit con la relase si usa chiamarlo V[numero].[numero]

git tag    fa vedere i tag nel nostro repository

git tag -a [nome versione] [ash commit da taggare] -m "[dicitura relase]"  per taggare un commit.

i tag sono come i rami, cioè locali.
per sincronizzare i tag usare
git push origin [nome del tag].

per taggare ultimo commit senza messaggio usare

git tag [nome del tag]

per eliminare un tag

git tag -d [nome del tag]


Passiamo alle bare repository

si intende solo i file dentro .git un bare repository non ha la working directory.

per clonare una repository solo il bare,
git clone [link repository] --bare

ho provato a fare una cartella nas locale dal quale clonare il bare repository: ti fa anche la working directory. ricorda che con il pwd puoi prendere il path assoluto.
